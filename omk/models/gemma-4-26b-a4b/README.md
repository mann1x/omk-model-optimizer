# Gemma-4-26B-A4B-it — agentic BF16 recovery (bm-889 sft11)

**Published:** [ManniX-ITA/gemma-4-26B-A4B-agentic](https://huggingface.co/ManniX-ITA/gemma-4-26B-A4B-agentic)
(BF16 safetensors) · [ManniX-ITA/gemma-4-26B-A4B-agentic-GGUF](https://huggingface.co/ManniX-ITA/gemma-4-26B-A4B-agentic-GGUF)
(F16, Q8_0, Q6_K, Q4_K_M + imatrix) · corpus
[ManniX-ITA/gemma-4-26B-A4B-agentic-sft](https://huggingface.co/datasets/ManniX-ITA/gemma-4-26B-A4B-agentic-sft) ·
[ManniX-ITA/hermes-agent-kimi-traces-gemma4-31b](https://huggingface.co/datasets/ManniX-ITA/hermes-agent-kimi-traces-gemma4-31b).

**Mode:** [BF16 recovery](../../docs/bf16-recovery.md), SFT (`--loss ce`). No quantizer, no layout: the model's own
bf16 weights of attention, dense MLP, router and routed experts are trained; embedding, norms and vision tower are
untouched and exported byte for byte.

## Why

Stock `google/gemma-4-26B-A4B-it` falls into reasoning and tool-call loops on long agentic coding tasks (the same
paragraph or the same call again and again until the context or wall clock runs out). The goal: remove the loops
while keeping the model's own voice and skills — no distillation into another model's style, no quantization.

The fix is an **on-policy SFT**: the training turns are the model's *own* answers, regenerated turn by turn in its own
chat template and kept only when a validator found no loop, no foreign token, and a tool call equivalent to the one
the recorded tool output answers. One source (`kimi31b`) is regenerated by the bigger sibling Gemma-4-31B-it.

## Results

### Head-to-head with the base model (SDK 4.100.277, 20 runs each)

Agentic gate: automaticum `gate-owner/manic_miner_plain`. The task is to repair a broken HTML game until `./run_game`
reports that it loads, reaches play and passes 23 logic checks (oracle-checked). Setup:
- Cerebriline SDK 4.100.277 agent, VS Code host profile, LSP diagnostics after every edit and the `check_file` /
  `ask_lsp` tools on, browser off.
- Both models as BF16 GGUF (eos 106) on the same opencoti llama.cpp build, each on its own RTX PRO 6000 Blackwell on
  bs2, f16 KV cache, Gemma-4 assistant drafter.
- Thinking on (effort high); temperature 0.8 / top_p 0.95 / top_k 64 / min_p 0 / presence_penalty 0.025.
- 1,800 s wall per run, one run at a time per model.

The two arms differ only in the model, checked from each run's recorded provenance
([`sft11/eval/automaticum/`](sft11/eval/automaticum/)).

| | base `gemma-4-26B-A4B-it` | **sft11 final = published** |
|---|---|---|
| runs finished within the 30-minute budget | 3 / 20 (15 %, Wilson 5–36 %) | **12 / 20 (60 %, 39–78 %)** |
| finished by 10 / 20 / 30 min | 0 / 15 / 15 % | **25 / 50 / 60 %** |
| reasoning blocks cut for repeating themselves, per run (median) | 8 | **1** |
| … per model-hour | 18.1 | **2.9** |
| runs with no reasoning-loop cut | 0 / 20 | **9 / 20** |
| tool calls per model-minute (median) | 0.9 | **3.3** |
| game runs per run (median) | 2 | **5** |
| longest single model turn (median) | 213 s | **108 s** |
| failures where the game never loaded | 17 of 17 | 6 of 8 (the other 2 reached 17/23 and 21/23) |

Pass/fail difference: Fisher exact two-sided p = 0.0079.

**The pass rate is relative to the 30-minute budget.** It is the share of runs that finished within it, not an
absolute success rate. The test measures what the SFT changes in a definite amount of time: how much of the budget
goes to loops, and how quickly the model gets from a broken file to a working game. With more time both models would
pass more often and the gap would likely narrow, but not by much. In the owner's extended manual testing of the base
model and the pruned 98-expert variants (v7-coder, v9-agentic), a run that does not converge quickly becomes steadily
more likely to loop, so the base model needs one to two hours or more to pass, or ends in massive loops.
Anti-repetition sampling hides the loops but costs the model much of its effectiveness and its ability to converge.
With the SFT, `presence_penalty 0.025` alone is enough to make it virtually loop-free.

Total reasoning per run is about the same for both models (226k vs 230k characters); how it is spent is not. The base
model spends about twice the generated tokens per tool call (3,866 vs 2,100), and its reasoning repeats until the
guard cuts it, so it tests the game less often.

Known weaknesses of sft11:
- **Repeating refused calls.** When an edit is refused it is more likely to send the same call again (failed-run
  median of 6 repeated-call warnings vs 0 for base).
- **Degenerate bursts.** In 2 of 20 runs it emitted the same refused `editor` call 310 and 320 times in one response.
  Both began with a call whose `start_line` was dropped. The base model hit that same refusal in 7 runs and never
  burst.
- **Harness stops.** Each model had one run stopped by the harness for repeating a call.
- **Serving speed.** Its server generated 4 % fewer tokens/s (168 vs 176). Draft acceptance was the same (88.7 vs
  89.8 %), so the drafter does not explain the gap.

Full analysis (loops, guards, length, time, behaviour, LSP, hygiene, failed-call classes, per-run table):
[`sft11/eval/results/h2h_report.md`](sft11/eval/results/h2h_report.md); how it was produced:
[`sft11/eval/`](sft11/eval/).

### Earlier gates (10 runs per checkpoint)

Same task, `manic_miner`. Loop rate = guard cuts and blocks per model-hour.

| checkpoint | pass | loops / model-hour |
|---|---|---|
| base `gemma-4-26B-A4B-it` | 1 / 10 | 9.2 |
| sft11 step 400 | 4 / 10 | 9.7 |
| sft11 step 800 | 5 / 10 | 3.1 |
| **sft11 final (step 2108) = published** | **5 / 10** | **2.0** |

Same gate for every row: SDK 4.100.266, thinking on (effort high), Gemma-4 default sampler (temperature 1.0,
top_p 0.95, top_k 64, min_p 0, no penalties). With the owner's deployment sampler (temperature 0.8, top_p 0.95,
top_k 64, min_p 0, presence_penalty 0.025), SDK 4.100.276 and the owner's full task prompt, the final checkpoint passed
7 of 8 finished runs. In the owner's VS Code plugin (same server, seed file and sampler) it fixed the game in 3 of 3
sessions in 6–10 minutes, with no loops seen.

Training evals (logged every 200 steps):

| | init | step 2108 |
|---|---|---|
| CE on the corpus's own held-out rows (11 families, mean) | 0.2808 | **0.2631** |
| held-out agentic windows vs the Gemma-4-31B teacher: top-K KL / top-1 / ppl | 0.118 / 0.930 / 1.259 | 0.147 / 0.929 / 1.260 |

The teacher-KL set measures drift from Gemma-4-31B on base-model answers; it is a diagnostic, not a target (the run is
SFT, not distillation), and top-1 agreement and perplexity there stayed flat.

## How the corpus was built

Scripts as run (host paths included) in [`sft11/corpus/`](sft11/corpus/).

**On-policy sources** (10), [`sft11/corpus/sft2/`](sft11/corpus/sft2/):

1. `sft2_fetch.py` (seed 889, ≤ 3,000 rows per source): whole rows read at seeded byte offsets of the pinned upstream
   files, excluding the 7,232 rows an earlier run trained on.
2. `sft2_jobs.py` (≤ 4 assistant turns per conversation, foreign reasoning stripped; hermes: 3,000 seeded pool lines)
   → 54,102 jobs; `sft2_plen.py --window 16384 --min-gen 4096` → 49,499; jobs whose context ends on an assistant turn
   dropped → 49,260; `sft2_cap.py` per-source caps → 20,734.
3. `sft2_generate.py` against Gemma-4-26B-A4B-it BF16 on vLLM 0.20.2
   ([`serve/start-8261-…-safe.sh`](sft11/serve/): `--reasoning-parser gemma4`, thinking on,
   `served_template_6a1015c4.jinja` = the model's chat template as served, the `gemma4_safe` tool parser), sampler
   temperature 1.0 / top_p 0.95 / top_k 64 / min_p 0, 4 attempts, first `sft2_validate.py` pass kept.
4. `sft2_rescore.py` with the loop, control-token and text-beside-call rules → 14,080 kept; `jobs_v2.py` refill of the
   rejected turns plus fresh jobs, `sft2_chain3.sh … --samples 3 --seed 890 --quota {...}` → +2,017 → **16,097 turns**.
5. `sft2_assemble.py` (eval ≥ 64 per source, split by source row; history as `score: false`), `sft2_resplit.py`
   (whole rows moved eval → train where the 200-gram overlap gate fired: cp 8, hermes 15, opencode 3, swe 2 turns).

**kimi31b** (Gemma-4-31B-it), [`sft11/corpus/kimi31b/`](sft11/corpus/kimi31b/): `sft6_kimi_jobs.py` (seed 889; 300
validator-passing ≤ 8,192-token rows by category quota → 1,153 jobs), `sft2_plen.py --window 12288 --min-gen 2048`,
`sft2_generate.py` against the Gemma-4-31B-it BF16 GGUF ([`serve/start-8263-…`](sft11/serve/): llama.cpp, thinking
on, 4 slots × 12,288) → 725 kept of 1,153, `sft6_p34.sh` assembly → 693 train / 32 eval; the overlap gate then removed
the 4 eval rows of one source conversation (28 eval). Details on its
[dataset card](https://huggingface.co/datasets/ManniX-ITA/hermes-agent-kimi-traces-gemma4-31b).

**Render** ([`sft11/corpus/render/`](sft11/corpus/render/)): `omk_qad.rollouts --history-reasoning strip --seq 16384
--pack` with the overlay code, then the train/eval overlap gate (0 hits) and `window_check.py` (every window starts at
`<bos>`, none cuts a conversation).

Regeneration at temperature 1.0 is not bit-reproducible; the published conversations and windows are, and training
from them is.

## Reproduce

```bash
git clone -b omk-main https://github.com/mann1x/omk-model-optimizer && cd omk-model-optimizer
bash omk_qad/conda_env/setup_conda_env.sh                       # env omk-modelopt
# the code the run used: omk_qad at 62740da07 + the overlay
git worktree add ../omk-sft11 62740da07
cp -r omk/models/gemma-4-26b-a4b/sft11/train/omk_sft2_code/omk_qad/* ../omk-sft11/omk_qad/
export PYTHONPATH=$PWD/../omk-sft11 ENV=$(conda info --base)/envs/omk-modelopt/bin/python

hf download google/gemma-4-26B-A4B-it --revision 4d7ae4984b7db7de8f8457170b3f1a419ee76d52 --local-dir models/gemma-4-26B-A4B-it
hf download ManniX-ITA/gemma-4-26B-A4B-agentic-sft --repo-type dataset --local-dir data/sft11
(cd data/sft11 && sha256sum -c SHA256SUMS)

# a cache dir is required for seq + eval rows; with --loss ce it supplies no training targets.
# Exact run: cache_teacher_r4 (Gemma-4-31B GGUF teacher, commands in omk/docs/bf16-recovery.md) + its evalset_heldout.
# Without it: any small cache at --seq 16384, and drop --eval-set heldout (diagnostic only; weights unchanged).
$ENV -m omk_qad.train --phase train --mode bf16 --model models/gemma-4-26B-A4B-it --cache cache_teacher_r4 \
    --out runs/g4_bf16_sft11 --train-scope classes:attention,dense_mlp,router,routed_experts --bs 2 --steps 2108 \
    --lr 4.74e-6 --fp-lr 4.74e-6 --warmup 10 --seq 16384 --loss ce --mtp freeze \
    --sft-data "$(ls data/sft11/render/*.train.roles.jsonl | paste -sd,)" \
    --sft-eval "$(ls data/sft11/render/*.eval.roles.jsonl data/sft11/eval/sft_mix_v*_eval.roles.jsonl | paste -sd,)" \
    --eval-set heldout --eval-every 200 --save-every 100 --snapshot-every 100 --snapshot-keep 2 --guard-ratio 3

CUDA_VISIBLE_DEVICES= $ENV -m omk_qad.train --phase export --mode bf16 --model models/gemma-4-26B-A4B-it \
    --load runs/g4_bf16_sft11/stage1/final.pt --out-hf out/gemma-4-26B-A4B-agentic
```

The run's own launcher (memory guard, early snapshot links, W&B) is [`sft11/train/sft11_train.sh`](sft11/train/sft11_train.sh).

  (`calib_train.txt`, sha256 `33fef70c…`, 3,043 documents, 4.91 M tokens), all 9,590 chunks, `--parse-special`;
  published in the GGUF repo under `calibration/` next to `imatrix.dat` (sha256 `609a0a04…`).
- `llama-quantize --imatrix imatrix.dat` for Q4_K_M, Q6_K, Q8_0 (Q8_0 carries the imatrix KV tags but ggml's Q8_0
  quantizer does not use importance weights).
